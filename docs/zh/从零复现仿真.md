# 新人从零复现 SurgicAI 仿真

这份文档假设你刚拿到一台 Ubuntu/WSL2 机器，不知道 AMBF、ROS、DA、FP、
policy 分别在哪里。请按顺序执行，不要一上来直接跑总脚本。

## 0. 先明确“复现”有三层

| 层级 | 运行内容 | 额外资产 | 它证明什么 |
|---|---|---|---|
| L0 代码自检 | Python、控制器、hand-eye synthetic | 无 GPU、无 AMBF | 下载完整、接口和纯代码可执行 |
| L1 Reach 重放 | AMBF + 冻结 SIM-S3 bank + D2/RL | AMBF、SRC；RL 已随 Git 发布 | 同一 reset/goal 下控制链能否重现 |
| L2 完整感知重算 | 渲染 RGB/GT → DA/GT depth → FP → gate → Reach | 新 DA checkpoint、FP image、GPU | 从像素重新得到 goal 后能否 Reach |

`[测量]` 原正式结果是 SIM-S3 40/40 过首帧门、门后 0/40 翻转，随后
SIM-S4 deployment-proxy D2 Reach 29/30；报告分别为
`docs/evidence/SurgicAI_SIM_S3_live_needle_initial_gate_20260811.md` 和
`docs/evidence/SurgicAI_SIM_S4_deployment_proxy_reach_20260811.md`。

`[推断]` L1 是控制/重放复现，不是 DA/FP 重算；只有 L2 才能声称感知计算也被
重新执行。`data/reference/sim_s3_20260811/README.md` 明确记录了这个边界。

## 1. 机器与系统

### 1.1 推荐配置

- Ubuntu 22.04，或 Windows 11 + WSL2 Ubuntu 22.04；
- ROS 2 Humble、Python 3.10；
- NVIDIA GPU；完整 DA+FP 推荐至少 16 GB 显存，32 GB 更宽裕；
- 至少 80 GB 空闲磁盘；
- Docker + GPU passthrough。

ROS 2 Humble 的 Tier-1 Linux 目标就是 Ubuntu 22.04；不要在 24.04/Jazzy 上
直接套本合同后仍称为严格复现。安装 ROS 请使用 ROS 官方 Humble Ubuntu 指南。

### 1.2 WSL2 基础检查

在 Windows PowerShell：

```powershell
wsl --status
wsl -l -v
nvidia-smi
```

进入 Ubuntu：

```bash
cat /etc/os-release
python3 --version
nvidia-smi
docker version
```

任何一项失败，先修系统层；不要通过改 Python 代码绕过 GPU/驱动错误。

`[测量]` 历史上带空格的 OneDrive 路径使嵌套命令解析失败；发布取舍和路径合同见

## 4. 安装 AMBF、ROS bridge 与 SRC

### 4.1 ROS 2

按 ROS 官方 Ubuntu deb 指南安装 Humble，然后确认：

```bash
source /opt/ros/humble/setup.bash
ros2 --help >/dev/null
python3 -c 'import rclpy; print("rclpy OK")'
```

### 4.2 AMBF 3.0

```bash
mkdir -p "$HOME/surgicai_external"
cd "$HOME/surgicai_external"
git clone https://github.com/WPI-AIM/ambf.git
mv ambf ambf.tmp
mv ambf.tmp ambf

sudo apt update
sudo apt install -y build-essential cmake libasound2-dev libgl1-mesa-dev \
  libglx-dev libegl1-mesa-dev xorg-dev libusb-1.0-0-dev libyaml-cpp-dev \
  libboost-all-dev freeglut3-dev python3-colcon-common-extensions python3-pykdl

cd "$HOME/surgicai_external/ambf/core"
mkdir -p build

cmake .. -DCMAKE_BUILD_TYPE=Release
```

本项目历史资产来自 AMBF 3.0 快照；上游 Git 分支/依赖若变化，必须记录
`git rev-parse HEAD`。没有已冻结的 AMBF commit 元数据时只能称环境重建，不能称
bit-for-bit 重建；这是当前发布包的已知 provenance 限制。

## 5. 安装 RL Python 依赖

先按你的 CUDA/驱动用 PyTorch 官方 selector 安装匹配版本，再安装本项目依赖：

## 6. 配置路径并生成 launch

```bash
cd "$HOME/suturing-policy-sim2real"
cp configs/pipeline.env.example configs/pipeline.env
nano configs/pipeline.env

python scripts/prepare_ambf_launch.py \
  --src-root "$HOME/surgicai_external/surgical_robotics_challenge" \
  --output-dir "$HOME/.cache/surgicai/launch"
```

检查 `configs/pipeline.env`：

- `SURGICAI_PUBLIC_ROOT` 是本仓库；
- `AMBF_ROOT` 指向含 `core/build/bin/ambf_simulator` 的目录；
- `SRC_ROOT` 指向含 `ADF/` 的目录；
- `ROS_DOMAIN_ID` 是未使用的 1..232 数字（Fast DDS 的 233 会越过 UDP 端口范围）；
- `SIM_S3_STEREO_LAUNCH`/`SIM_S4_STEREO_LAUNCH` 是刚生成的 YAML；
- `SIM_S4_MODEL` 默认指向随 Git 发布的 M3-100k。

不要把 `configs/pipeline.env` 提交到 Git；它可能包含本机路径。

## 7. L1：先重放冻结感知结果

L1 不需要 DA checkpoint 或 FP Docker。它使用随仓库发布的 40 条 SIM-S3
紧凑 bank，重新启动 AMBF 并跑 GT/FP 两套 frozen goal 的控制 A/B。

```bash
cd "$HOME/suturing-policy-sim2real"
source .venv/bin/activate
source /opt/ros/humble/setup.bash
source "$HOME/ambf_ros_ws/install/setup.bash"

python scripts/doctor.py --profile reach --config configs/pipeline.env --check-domain-clean

# 先跑 2 episode 冒烟
python scripts/run_simulation.py \
  --stage s4 --profile smoke --goal both --controller d2
```

结果根会打印在最后一行。检查：

```bash
python scripts/inspect_results.py "$HOME/surgicai_runs/pipeline_smoke_<时间戳>"
```

正式复现：

```bash
python scripts/run_simulation.py \
  --stage s4 --profile formal --goal both --controller d2
```

`[测量]` 参考正式结果中 deployment-proxy B 为 29/30；但重新构建的 AMBF/SRC
版本若未冻结到同一 commit，数值漂移必须如实报告，不能删失败 episode。

## 8. L2：从像素重算 DA → FP → Reach

### 8.1 FoundationPose

```bash
cd "$HOME/surgicai_external"
git clone https://github.com/NVlabs/FoundationPose.git
cd FoundationPose
git checkout a1b694b83e633c2cb6115b9063d940a687759392
```

上游官方推荐 Docker。构建/拉取后，本项目要求本地存在标签：

```bash
docker image inspect foundationpose:blackwell >/dev/null
```

`foundationpose:blackwell` 是项目实际运行标签，不是上游通用标签。若你的 GPU
需要另一个镜像，用 `SIM_S3_FP_IMAGE` 显式指定，并记录 image ID/digest；不要静默
替换后仍与历史数字直接比较。历史使用的 image digest 见
`docs/MODEL_ASSETS.md`。

### 8.2 新 DA checkpoint

把实验室提供的 checkpoint 放到：

```text
$HOME/surgicai_models/p5a_vitl_fp32_best.pth
```

验证：

```bash
sha256sum "$HOME/surgicai_models/p5a_vitl_fp32_best.pth"
```

必须得到：

```text
fc46bead4a5ea0e4122566bb88b93932aa82f110ee98281b5fcb09f499c9ec88
```

这个 3.8 GB 文件不能放进普通 Git；没有它时，L0/L1 仍可完整运行，但 L2 的
DA 分支必须停在 `D9-E32-DACKPT`，不能拿 GT depth 冒充 DA。

### 8.3 完整冒烟与正式运行

```bash
python scripts/doctor.py --profile full --config configs/pipeline.env --check-domain-clean

# 2 reset S3 + 2 episode S4
python scripts/run_simulation.py \
  --stage full --profile smoke --depth da --goal both --controller d2

# 40 reset S3 + 30 episode S4
python scripts/run_simulation.py \
  --stage full --profile formal --depth da --goal both --controller d2
```

runner 的实际顺序是：

```text
domain clean -> AMBF ready state -> 40 reset/capture -> DA inference
-> FP register/candidates -> support-plane/R_rest gate -> goal banks
-> AMBF restart -> GT cell -> AMBF restart -> FP cell -> manifest
```

## 9. 怎么替换 GT、DA、FP、controller

所有替换都从同一个入口做，避免手改 30 个 flag：

```bash
# GT depth + FP：只测试 FP，不测试 DA
python scripts/run_simulation.py --stage full --profile smoke \
  --depth gt --goal fp --controller d2

# DA depth + GT goal：DA/FP会被计算，但控制绕过FP，用于控制上限
python scripts/run_simulation.py --stage full --profile smoke \
  --depth da --goal gt --controller d2

# 冻结 FP goal + RL policy
python scripts/run_simulation.py --stage s4 --profile smoke \
  --goal fp --controller rl

# 同一 bank 下 GT/FP goal × D2 配对
python scripts/run_simulation.py --stage s4 --profile formal \
  --goal both --controller d2
```

含义：

| 开关 | `gt` | `da/fp/rl` |
|---|---|---|
| `--depth` | AMBF metric depth，特权输入 | 新 DA 预测 depth |
| `--goal` | 直接从 AMBF needle pose 算 goal | 从 FP gated pose 算 goal |
| `--controller` | 不适用 | `d2` 解析 servo；`rl` checkpoint action |

`--goal both` 才是严格的同 reset 配对 A/B。单跑一边只能回答“它是否能跑”，不能
可靠归因两边差值。

## 10. 成功判定和产物

每次顶层运行必须有：

```text
pipeline_status.json
doctor.json
sim_s3/MANIFEST.sha256                 完整感知时
sim_s3/reset_bank.json
sim_s3/da_result.json
sim_s3/fp_gate/result.json
sim_s4/banks/*.json
sim_s4/A_*/episodes.jsonl
sim_s4/A_*/result.json
sim_s4/B_*/episodes.jsonl
sim_s4/B_*/result.json
sim_s4/MANIFEST.sha256
```

不要只看进程退出码。历史 ROS/RAL 在产物写完后可能 teardown abort；是否完成由
`episode_records` 数量、`status.txt` 的 `artifact_complete=1` 和 manifest 决定。
