# 真机主代码逐文件、逐状态、逐分支白话讲义

这份讲义不是运行手册，也不是项目摘要。它的目标是：你打开代码文件时，能把每一段
代码翻译成人能理解的动作；然后知道哪一段已经有实现、哪一段只有接口、哪一段还缺
真实参数。

对应代码根目录：

```text
packaging/public_repo_git_d9/ros2_ws/src/suturing_runtime/
```

本讲义覆盖 14 个核心 Python 文件、两个 real launch 和一份 YAML。代码总入口是
`launch/real_read_only.launch.py`，不是 AMBF 的 `Approach_env.py`。`[测量]`（证据：
`packaging/public_repo_git_d9/ros2_ws/src/suturing_runtime/launch/real_read_only.launch.py:1-27`）

## 0. 先把 ROS 程序想成一群各司其职的人

一个 ROS node 可以想成一个独立工作人员：

- `subscription`：他的收件箱。某个 topic 来消息，就调用一个 callback；
- `publisher`：他的发件箱；
- `service`：不是持续来信，而是操作者明确按一次按钮、等待一次回答；
- `parameter`：启动时读的配置；
- `timer`：固定频率执行；
- `TF`：一个共享坐标变换数据库。

这里故意不用一个 2000 行“大主程序”。原因是：DA 挂掉时，camera adapter 和安全
executor 仍能报告自己的状态；mask 错时间戳时，系统能明确停在 R3/R4，而不是最后只
得到“policy failed”。`[推断]`

### 三种消息时效

1. **连续消息**：相机和 `measured_cp`。新消息不断覆盖旧消息。
2. **一次初始化证据**：snapshot、depth、mask、FP candidates、frozen goal。
3. **明确命令**：capture、人工 confirm、arm、execute、stop。

初始化证据使用 `TRANSIENT_LOCAL`：publisher 发完后仍保留最后一条，后来启动的
subscriber 能收到。连续传感器通常使用 sensor-data QoS。`[测量]`（证据：
`snapshot_node.py:36-49`；`guarded_pose_executor.py:52-60`）

## 1. 启动文件究竟做了什么

文件：`launch/real_read_only.launch.py`。

### 第 1–6 行：导入“如何启动 ROS 节点”的工具

这些 import 不处理图像，也不控制机器人。它们让 Python 可以构造一个
`LaunchDescription`，找到已安装 package 的 share 目录，并把 YAML 路径传给每个节点。

### `config = LaunchConfiguration("config")`

白话：不要在每个代码文件里写死 JHU 路径；启动命令可以传另一份 YAML。没传时用包内
`config/jhu_real.yaml`。

### launch 中 Node 的顺序

代码声明 adapter、snapshot、DA、depth/mask adapter、bundle join、FP candidate
adapter、flat gate、PSM camera bridge、goal builder、supervisor、executor。

launch 声明顺序不是“前一个完全跑完才启动下一个”。ROS 会近乎同时启动它们；真正的
依赖由 topic 控制。DA 即使先启动，也要等 snapshot；goal builder 即使先启动，也要等
gated pose。`[测量]`（证据：`launch/real_read_only.launch.py:12-28`）

### 为什么 read-only launch 里也有 executor

因为我们要在不运动时检查目标和 preview 逻辑。launch 最后一行把
`enable_output=False` 覆盖进 executor；因此 executor 可以订阅、算状态，但不会创建
`/PSM1/servo_cp` publisher。`[测量]`（证据：
`launch/real_read_only.launch.py:27-28`；`guarded_pose_executor.py:42-51`）

### guarded launch 的唯一区别

`real_guarded.launch.py` 把 `enable_output=True`，同时要求命令行传入
`operator_acknowledgement`。但是这仍不自动 arm，也不自动 execute。`[测量]`（证据：
`launch/real_guarded.launch.py:8-30`；`guarded_pose_executor.py:67-87`）

## 2. `config/jhu_real.yaml`：它不是注释文件，而是现场合同

YAML 第一层名称必须与 node name 相同；`ros__parameters` 下的值会覆盖代码默认值。

### adapter 参数

```yaml
raw_left_image: /jhu_daVinci/left/image_rect
raw_psm_pose: /PSM1/measured_cp
raw_psm_pose_type: geometry_msgs/msg/PoseStamped
```

白话：告诉 R0“实验室消息从哪里来、是什么类型”。topic list 只能证明名字存在，不能
证明 `measured_cp` 是 PoseStamped 还是 TransformStamped，所以 type 仍要 preflight。
`[测量]`（证据：`config/jhu_real.yaml:1-12`；`topic_preflight.py:11-48`）

### DA 参数

`enabled=false` 是安全默认。改成 true 后，`checkpoint_path` 和
`depth_anything_repo` 必须是绝对路径。代码不会从当前目录猜，也不会下载另一个模型。
`expected_checkpoint_sha256` 把“文件名 best.pth”升级为“内容完全相同”。`[测量]`
（证据：`config/jhu_real.yaml` 的 `metric_da_depth` 段；
`metric_da_depth.py:45-68,76-89`）

### flat gate 参数

`plane_configured=false` 表示真实 phantom 法向还没测。两个 `[0,0,1]` 只是占位值，
不是测量；只把 false 改成 true 而不确认 frame/normal 是错误操作。`[测量]`（证据：
`config/jhu_real.yaml` 的 `needle_flat_gate` 段；`needle_flat_gate.py:41-50`）

### executor 参数

速度、最大初始误差、workspace 和 timeout 都在 YAML。它们不是 RL 成功判据，而是最后
一层真机运动安全限制。当前 workspace 是占位盒，未现场确认前不应开输出。`[假设]`

## 3. R0：`dvrk_topic_adapter.py` 逐段翻译

### 类启动：为什么有一大组 defaults

`defaults` 同时列 raw 名和 canonical 名。raw 名是实验室可能变化的接口；canonical 名
是项目内部稳定接口。以后换 PSM2，只改 YAML，不改下游 DA/FP/control 文件。
`[测量]`（证据：`dvrk_topic_adapter.py:16-37`）

### 第 39–46 行：创建项目内部发件箱

- `pose_pub` 发标准化 PSM pose；
- `twist_pub` 发速度；
- `jaw_pub` 发 jaw joint；
- 四个 camera publisher 发左右图和左右内参；
- `status_pub` 每秒发计数。

这里只创建状态 publisher，没有 raw servo publisher，所以 R0 本身不可能动机器人。
`[测量]`（证据：`dvrk_topic_adapter.py:39-49`）

### 第 50–68 行：把 raw topic 接到 callback

图像、K、速度、jaw 都走 `_relay`：收到什么就发布什么，连 header 也不改。

PSM pose 需要多一步，因为两个版本的 dVRK 消息不同：

- 配置写 `PoseStamped`，callback `_pose_stamped` 直接转发；
- 配置写 `TransformStamped`，callback `_transform_stamped` 把 translation/rotation 字段
  搬进 PoseStamped；
- 其他字符串立即抛 `D10-E11`，不尝试猜。

`[测量]`（证据：`dvrk_topic_adapter.py:50-68,72-89`）

### `_publish_pose` 为什么补 fallback frame

若 raw message 的 frame_id 为空，代码写入配置的 `fallback_psm_frame`。这只是兼容旧
publisher；若 fallback 名字与实际坐标系不一致，后面数学虽能运行，物理意义仍错，所以
preflight 必须保存 frame。`[推断]`

### `_status`

每秒把七路消息收到多少条写成 JSON，并写 `command_capability=false`。这让你能区分：
“topic 名存在但没有消息”和“消息正常、只是下游没处理”。`[测量]`（证据：
`dvrk_topic_adapter.py:91-95`）

### `main`

`rclpy.init()` 初始化 ROS；构造 node；`spin()` 等 callback；Ctrl-C 后销毁 node；只有
context 仍 active 才 shutdown，避免 launch 已 shutdown 后重复调用产生假 traceback。
`[测量]`（证据：`dvrk_topic_adapter.py:97-104`）

## 4. R1：`snapshot_node.py` 逐段翻译

### 内部状态

```text
self.left/right            最近30张左右图
self.left_info/right_info  最近一份内参
self.sequence              本进程第几次成功capture
```

图像用 deque 是为了在右队列中找最接近左图时间戳的帧；camera info 当前只保留最新一份。
`[测量]`（证据：`snapshot_node.py:22-35`）

### 为什么发布五个输出

四个是左/右 image/K；第五个 snapshot JSON 保存 init ID、左右 stamp、frame、尺寸、
stereo skew 和 wall time。图像 header 是算法输入身份；wall time 只用于日志。
`[测量]`（证据：`snapshot_node.py:36-49,86-98`）

### 平时收到图像时做什么

只放进 deque。没有“每帧跑 DA”。这就是 frozen-goal 首次 demo 与 live tracking 的结构
区别。

### capture service 的完整判断顺序

1. 任一路图或 K 从未收到：`E101`；
2. 取最新左图；遍历右 deque，选绝对时间差最小者；
3. 左右差 >30 ms：`E102`；
4. 左图距离当前 ROS 时间 >0.75 s：`E103`；
5. 任一 camera frame 为空：`E104`；
6. 左 K 尺寸与左图不同：`E105`；
7. 全部通过才复制并锁存消息。

`[测量]`（证据：`snapshot_node.py:56-98`）

### 这里还有一个真实未决项

当前 camera info 取“最新一份”，bundle 后面要求它与图像同 stamp。若现场 driver 只在
启动时发一次 stamp=0 的 latched K，R4 会拒绝。正确修法应是给 K 建 calibration-version
合同，而不是把 K 的 stamp 偷改成图像 stamp。`[假设]`

## 5. R2：`metric_da_depth.py`——真正的 DA 在代码里怎样工作

这是上一版缺失、这次补上的部分。它不是 dummy publisher，已用 3.8 GiB checkpoint
在 CUDA 上实际输出 `32FC1`。`[测量]`（证据：
`records/logs/SurgicAI_D13_real_DA_and_codewalk_20260818.md`）

### 文件顶部的 SHA 和 MODEL_CONFIGS

SHA 是模型内容身份证。`MODEL_CONFIGS["vitl"]` 规定 backbone 的 encoder、feature
width 和四层 channels。checkpoint 保存参数，不保存可执行 Python 类，所以加载前必须
用同一结构造出空模型。`[测量]`（证据：`metric_da_depth.py:22-32`）

### `sha256()` 为什么读 1 MiB chunks

checkpoint 约 4 GB。一次 `read()` 会额外占数 GB 内存；循环读小块只保留一个小 buffer，
最终 digest 对整个文件仍完全敏感。`[测量]`（证据：`metric_da_depth.py:34-39`）

### `__init__` 的安全顺序

1. 声明 enable、路径、device、SHA、输入输出 topic；
2. 创建 depth/status publisher；
3. 若 `enabled=false`，发 `D13-E201-DA_DISABLED`，不 import torch、不占 GPU；
4. enabled 才调用 `_load_model()`；
5. 成功加载后才订阅 snapshot RGB；
6. 发布 READY。

checkpoint 错时不会出现“node 已订阅图像但每帧悄悄失败”。`[测量]`（证据：
`metric_da_depth.py:42-70`）

### `_load_model()` 的文件检查

- checkpoint 必须是文件，否则 E202；
- DA repo 必须有 `depth_anything_v2/dpt.py`，否则 E203；
- 实际 SHA 必须同时匹配 YAML expected 和代码冻结 SHA，否则 E204。

双重 SHA 的目的：不能在 YAML 里把 expected 也改成未知模型 SHA 后绕过项目合同。
`[测量]`（证据：`metric_da_depth.py:76-89`）

### 为什么 torch/cv2 在这里才 import

read-only runtime 即使没有 CUDA/torch，也应能以 DA disabled 启动、检查相机和 dVRK。
只有用户明确 enable DA 时才要求完整 ML 环境。`[推断]`

### 内部 `MetricDepthModel` 的数学

Depth Anything backbone 原始输出 `relative`，它不是米。代码先 ReLU，再从 checkpoint
读取三个可学习量：

```text
scale = exp(clamp(log_scale))
shift = softplus(shift_raw) + 1e-4
bias  = softplus(bias_raw)
depth_m = scale / (relative + shift) + bias
```

最后夹在 `1e-6` 到训练参数 `max_depth`。因此这不是“普通 DA 相对深度乘一个固定比例”；
米制映射属于训练模型本身。`[测量]`（证据：`metric_da_depth.py:96-113`；
`src/perception/run_da_a1_checkpoint_eval.py:37-64`）

### checkpoint schema 检查

代码要求顶层有 `args` 和 `model`；然后检查 `encoder=vitl`、`input_size=518`、
`precision=fp32`；之后 `strict=True` 加载。缺 key、多 key、模型结构不同都停止。
`[测量]`（证据：`metric_da_depth.py:115-135`）

### `_decode_color()`

ROS Image 每行可能有 padding，所以不能直接 reshape H×W×3。代码先 reshape H×step，再
只取前 `width*3` bytes。支持 `rgb8` 和 `bgr8`；rgb8 翻转通道得到 OpenCV BGR。其他
encoding 报 E208。`[测量]`（证据：`metric_da_depth.py:138-143`）

### `_preprocess()` 每一步

1. BGR→RGB；
2. 不保持长宽比，强制拉成 518×518；
3. uint8 除 255 变 float 0–1；
4. 按 ImageNet mean/std 标准化；
5. HWC 转 CHW；
6. 增加 batch 维，得到 1×3×518×518。

“强制正方形”是训练合同；改成官方 keep-aspect `infer_image()` 会造成训练/推理不一致。
`[测量]`（证据：`metric_da_depth.py:145-151`；
`depth_audit_stage_a/da_exact_preprocess.py:24-45`）

### `_image()` 完整生命周期

1. 从 header 算 source stamp；同 stamp 已处理则返回；
2. 解码和 preprocess；
3. tensor 搬到 CUDA；
4. synchronize，开始计纯推理时间；
5. `torch.inference_mode()` 前向，取 `[0,0]` 的 518×518 depth；
6. synchronize，确保计时不是只算 kernel launch；
7. 双线性 resize 回原相机分辨率；
8. 强制 little-endian float32；
9. 检查全部 finite 且 >0；
10. 新建 ROS Image，**原样复制输入 header**，encoding=`32FC1`、step=`width*4`；
11. 发布 `/suturing/external/depth`；
12. status 记录 stamp、inference/total、min/max 和 checkpoint SHA。

异常发布 E210，不更新 `last_stamp_ns`，问题修好后同一帧仍可重试。`[测量]`（证据：
`metric_da_depth.py:153-181`）

### 真实验证数字如何理解

4×4 测试 RGB 的输出：same stamp、`32FC1`、64 bytes，推理 0.396 s，depth 0.0872–
0.1809 m。`[测量]` 这证明 ROS 解码→真实模型→ROS depth 接通，不证明真实 ECM 准确；
准确性必须等真实图像和参考几何。（证据：
`records/logs/D13_real_DA_and_codewalk_20260818/da_ros_smoke.json`）

## 6. R3：为什么 mask 仍然是外部输入

文件：`perception_input_adapter.py` 同时负责 depth 和 mask 的边界验收。

DA 已有冻结 checkpoint 和预处理，所以能写进 R2。mask 不同：人工 mask 缺 GUI；仿真
U-Net 标签来自 semantic ID；YOLO/SAM 没有冻结真机权重和阈值。因此正确行为是“接口
存在、来源不冒充完成”。`[测量]`（证据：
`records/logs/SurgicAI_SIM_S10_automatic_mask_bridge_20260813.md`）

### 内部状态和 callback

`self.reference` 保存 snapshot RGB 的 stamp/frame/width/height/encoding。收到 RGB 只更新
reference。收到 depth/mask 共同走 `_validate()`：无 snapshot 是 E201；逐项比 stamp、
frame、shape、encoding；有错 E202；depth 只接受 32FC1，mask 接受 mono8/8UC1；通过才
发布 canonical topic。`[测量]`（证据：`perception_input_adapter.py:33-57`；
`contract.py:31-52`）

DA 自己发布 external depth 后仍由另一个 node 再验一次，是因为 producer 自称 header
正确不等于边界应无条件相信它。

## 7. R4：`bundle_join_node.py` 怎样消灭异步拼错帧

`self.items` 是四格抽屉：rgb/info/depth/mask。每个 callback 放入最新消息深拷贝，然后
调用 `_try_emit()`。消息顺序不确定，所以无论谁最后到，都能触发检查。

`_try_emit()`：少 key 就等待；以 RGB 为 reference；检查 depth、mask、K 的 stamp/frame/
shape/encoding；有错 E301；同 stamp 发过则跳过；通过才同时发布四个 FP input 和 ready
JSON。`[测量]`（证据：`bundle_join_node.py:17-55`）

异步不是靠 sleep 解决，而是靠数据身份解决。DA 慢 5 秒也没关系，只要 header 仍属于
原始 RGB。

## 8. R5：`fp_candidate_adapter.py` 为何坚持“全部候选”

`self.ready` 保存 R4 当前允许的 stamp/frame。没有 ready 时 candidates 是 E402。

候选暂用 JSON，因为当前包没有自定义 ROS interface；代价是编译期类型安全弱，所以
adapter 手查 schema、stamp、frame、mesh_frame、非空 poses、position、quaternion、
score。通过后才发布 canonical candidates。`[测量]`（证据：
`fp_candidate_adapter.py:34-59`）

不只取 top-1，是因为 FP score 不是正确概率。PSM 审计 score AUC 0.330，needle 也出现
top-score 180°翻面；提前丢候选会让 R6 无法补救。`[测量]`（证据：
`records/logs/SurgicAI_P7e_PSM_frame_contract_audit_20260806.md:81`；
`PROJECT_STATE.md` §8 第20条）

真正 FP backend 还需订阅 RGB/depth/mask/K，加载针 mesh，执行 register，保存 overlay
和全部候选，再发布 JSON。当前 ROS 包尚未启动 FoundationPose 容器。

## 9. R6：`needle_flat_gate.py` 怎样在无 GT 时筛候选

四个量：`T_C_N` 是候选；`n_rest^N` 是 CAD 正确平放面的法向；`n_plane^C` 是真实
phantom 在 camera frame 的法向；候选法向是 `R_C_N n_rest^N`。

`select_flat_candidate()` 检查 N×4×4、score 和有限性；归一化 normal；对每个旋转计算
候选法向；点积后 acos；保留角度≤阈值；在有效候选中选 score 最大。没有 `abs(dot)`，
所以反面是 180° 而不是 0°。`[测量]`（证据：`contract.py:55-95`）

node 顺序：先清旧 pending；plane 未配置 E501；plane frame 不等于 candidate frame E505；
输入错 E502；无平放候选 E503；有候选发布 pending；默认等待人工；service true 才 gated，
false 丢弃，无 pending 是 E504。`[测量]`（证据：`needle_flat_gate.py:41-83`）

人工应看同一 source RGB 上的 mask、CAD 轮廓、针轴和 tip/base。当前 overlay UI 未实现。
normal 门也无法验证平面内 yaw、xyz 或 tip/base，因此人工不是形式动作。

## 10. R7A：`psm_camera_bridge.py` 把 measured_cp 变到 camera frame

输入语义 `T_B_E`，输出语义 `T_C_E`。callback 检查 camera frame 和 measured frame；
向 TF 查询 camera←base；超时 E603；构造 4×4 `T_C_B` 和 `T_B_E`；相乘
`T_C_E=T_C_B×T_B_E`；转回 PoseStamped，保留 measured stamp。`[测量]`（证据：
`psm_camera_bridge.py:26-45`）

hand-eye 不是拿来修 FP，而是让 dVRK kinematics 和 camera perception 能在同一坐标系
比较。

## 11. R7B：`approach_goal_builder.py` 从 needle pose 造抓取目标

`contract.py` 根据 needle radius 和 grasp angle 在针弧上选抓取点，沿局部 z 加 lift，
再乘固定 gripper orientation，得到 `T_N_G`。`[测量]`（证据：`contract.py:139-151`）

goal callback：已有 frozen 就忽略后续；检查 pose age/frame；查 `T_B_C`；构造 `T_C_N`；
算 `T_C_G=T_C_N×T_N_G`；再算 `T_B_G=T_B_C×T_C_G`；同时发布 camera/base goal；保存
frozen base goal。`[测量]`（证据：`approach_goal_builder.py:42-77`）

reset service 只清 `self.frozen`，不移动真实针。人工重摆后应 clear goal、capture 新帧、
重新走 R2–R7。

## 12. R8A：`pipeline_supervisor.py` 判断“资料齐不齐”

每个 callback 只记本机 monotonic receipt time 和 frame。`_snapshot()` 的基础必需是左右
图、左 K、PSM pose；参数决定是否还要求 depth/mask/needle/goal。连续 freshness 只检查
左右 RGB 和 PSM pose；初始化 latch 可以老但不能缺。`[测量]`（证据：
`pipeline_supervisor.py:53-73`）

READY 不等于能运动：status 永远写 `command_enabled=false`。运动 authority 属于 executor。

## 13. R8B/R9：`guarded_pose_executor.py` 从 goal 到 servo_cp

启动时只有 `enable_output=true` 且 acknowledgement 精确匹配才创建 command publisher；
否则不是“不发”，而是 publisher 根本不存在。`[测量]`（证据：
`guarded_pose_executor.py:42-51,67-70`）

它保存 measured/goal 与收到时间、armed、active、started_at。arm true 在 read-only 返回
E50；guarded 下也只授权，不运动。

`_fresh()` 检查 measured/goal 存在、measured 新鲜、两者 frame 等于 command frame。
frozen goal 不按 receipt age 判 stale。

`execute_once`：未 arm E55；缺/旧/frame 错 E51/E52/E54；算初始平移和 SO(3)；超差
E56/E57；当前或目标出 workspace E58；全过才 active。

20 Hz `_tick()` 每次重查 freshness；超时 E59；最大平移步长=线速度/频率，最大旋转
步长=角速度/频率；平移沿直线，旋转 quaternion SLERP；先发 preview，权限 OK 才发 raw
servo；到 tolerance 后停止并自动 disarm。`[测量]`（证据：
`guarded_pose_executor.py:89-160`；`contract.py:168-190`）

每步读新 measured pose，而不是积分旧 command，因此机器人没走到时不会被当成已到达。

当前没有 collision model、operating-state gate、force threshold、jaw close/lift、RL
inference。这是 bounded Reach，不是完整临床安全控制器。`[测量]`

## 14. `contract.py`：为什么数学放在无 ROS 文件

它包含 frame 比对、quaternion/matrix、needle→goal、SO(3) 距离、SLERP、bounded step、
workspace。纯函数不启动 ROS、没有 hidden state，所以 Windows pytest 可直接锁定行为。

`FrameContract` 是派生产品的身份证。quaternion 输入先归一化，零/非有限拒绝。SO(3)
距离用 `R_a^T R_b` 的 trace，不逐 Euler 角相减。bounded step 的平移按距离比例截断，
旋转按总角度 fraction 做 SLERP。`[测量]`（证据：`contract.py:1-199`）

### 14A. `message_contract.py`：把 ROS message 变成可比较身份证

`stamp_ns()` 把 ROS 的秒和纳秒合成单个整数。这样比较时间戳时不是两个字段分别判断，
也不会用浮点秒引入舍入误差。`image_contract()` 只提取 stamp、frame、宽、高、encoding，
得到 `FrameContract`；后面的 R4 比的是这张身份证，不逐字节比较整张图片。

`clone_message()` 使用 `deepcopy`。原因是 ROS Python message 是可变对象：R1 所谓“锁存”
必须保留一份独立副本，不能只保存指向队列中同一对象的引用。`[测量]`（证据：
`message_contract.py:1-27`）

### 14B. `topic_preflight.py`：为什么 `ros2 topic list` 还不够

`EXPECTED` 表给每个真机 topic 写允许类型。相机、内参、速度、jaw 必须收到至少一条消息；
`/PSM1/servo_cp` 是输出，只检查图里是否存在和类型，不要求收到消息。measured/servo pose
允许 `PoseStamped` 或 `TransformStamped` 两代 dVRK 合同。

节点等待 5 秒，同时查询 ROS graph 的声明类型和 callback 实际收包数。最后逐 topic 输出
`type_ok/messages_received/frame_id`；任一输入类型错或零消息，进程以 exit code 2 退出。
所以“topic 名在列表里”但 publisher 卡死，会被判失败。`[测量]`（证据：
`topic_preflight.py:1-56`）

一个尚未自动拒绝的点是空 `frame_id`：preflight 会把它记录出来，但当前 `failures` 只看
类型和消息数。现场审计必须人工检查该字段；后面的 snapshot/goal 节点仍会在关键边界拒绝
空 frame。`[测量]`（证据：`topic_preflight.py:38-48`；`snapshot_node.py:71-85`）

### 14C. `mock_topic_source.py`：它证明安装，不证明算法

mock 每 0.1 秒发布 4×4 黑色 RGB、固定相机内参、固定 PSM pose。收到 snapshot 后，它造
0.1 m 常深度和全白 mask；收到 FP ready 后，它造一个固定针候选。这样不用 AMBF、DA、
FP 或真机，就能检查所有 topic 名、QoS、JSON schema 和状态机是否连通。

这些值都是程序制造的正例：全白 mask 不是分割，固定候选不是 FoundationPose，常深度不是
DA。因此 mock 到 `READY_READ_ONLY` 只能叫 wiring smoke，绝不能写成感知成功。
`[测量]`（证据：`mock_topic_source.py:1-64`）

### 14D. `setup.py/package.xml`：为什么写了文件还可能 `ros2 run` 找不到

`setup.py` 的 `entry_points.console_scripts` 把命令名映射到每个 Python 文件的
`main()`；忘记加入这里，即使源码存在，`ros2 run suturing_runtime 名字` 也找不到。
`data_files` 决定 launch/YAML 是否安装到 `install/.../share`；所以改 config 后必须
重新 build 或使用 symlink install。

`package.xml` 声明 ROS message、TF、OpenCV 等系统依赖；PyTorch/CUDA 和外部
Depth-Anything-V2 源码没有被 pip 自动下载，因为版本必须与 GPU 主机和冻结配方显式匹配。
`[测量]`（证据：`setup.py:1-38`；`package.xml:1-31`）


## 15. 从 capture 到机器人开始移动的精确事件顺序

1. R0 连续转发相机和 measured_cp。
2. 操作者调用 capture。
3. R1 选一对左右帧，发布 snapshot。
4. DA 收左图，CUDA 推理，发布同 header external depth。
5. mask provider 对同一图发布 external mask。
6. adapter 验 depth/mask，发布 canonical 产品。
7. R4 四件齐全且身份证一致，发布 FP bundle/ready。
8. 外部 FP register，发布全 candidates。
9. R5 验 schema 与 bundle stamp/frame。
10. R6 清旧 pending，筛平放候选，等待人工。
11. 人看 overlay，confirm true。
12. gated pose 触发 goal builder。
13. R7 查 hand-eye，发布 camera/base goal 并冻结。
14. supervisor 返回 READY_READ_ONLY。
15. executor 收到 goal，但 read-only 下没有 command publisher。
16. 人观察 preview/overlay；若决定运动，停止 read-only，启动 guarded。
17. 再完整初始化，避免沿用旧进程 latch。
18. arm 只授权。
19. execute_once 检查初差、frame、workspace。
20. timer 根据新 measured_cp 发 bounded servo_cp。
21. 达标或 fault 后停止并 disarm。

任一步失败，下一步所需 topic 不出现，因此不会跨过缺口继续运动。

## 18. 为什么不直接把 4 GB checkpoint 放普通 GitHub

`[测量]` checkpoint 是 4,014,768,993 bytes，SHA=`fc46...ec88`。普通 GitHub object
超过 100 MiB 被拒；GitHub Free/Pro 的 LFS 单文件上限 2 GB，该文件也超过。Team 4 GB
或 Enterprise 5 GB LFS 才可能直接保存，但仍有 LFS 存储/流量成本。

因此仓库保存完整 R2 推理代码、bytes/SHA/模型合同、`models/da/` 标准位置和启动 SHA
校验；权重本体放 JHU OneDrive/实验室存储。若确认 Team/Enterprise 与 LFS 预算，再单独
启用 LFS，不能把 4 GB 二进制直接 `git add` 后期待普通 push 成功。
